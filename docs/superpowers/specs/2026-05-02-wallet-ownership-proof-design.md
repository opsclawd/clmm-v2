# Wallet Ownership Proof for Enrollment - Design

**Status:** Design approved, pending implementation plan
**Issue:** [opsclawd/clmm-v2#21](https://github.com/opsclawd/clmm-v2/issues/21)
**Date:** 2026-05-02
**Supersedes:** `docs/superpowers/specs/2026-04-20-wallet-ownership-proof-design.md`

## Problem

`POST /wallets/:walletId/monitor` currently enrolls the supplied wallet id directly. Anyone who knows a Solana wallet address can enroll it for monitoring without proving control of the wallet.

Replace the unsigned enrollment path with a challenge-response flow:

1. The app requests a backend challenge for the connected wallet.
2. The wallet signs the exact backend-generated message.
3. The backend verifies the message and Ed25519 signature.
4. The backend consumes the challenge and enrolls the wallet only after proof succeeds.

The stale 2026-04-20 design assumed prior PR state and backend-only delivery. This design starts from the current repo state and includes the app migration in the same release.

## Goals

- Require wallet ownership proof before monitoring enrollment.
- Migrate the app fully from `/monitor` to `/challenge` plus `/enroll`.
- Keep `/monitor` only as a non-enrolling tombstone endpoint.
- Preserve active challenge idempotency during the five-minute TTL.
- Couple final challenge consumption and monitored-wallet enrollment transactionally.
- Return structured, stable error codes.
- Add explicit message-signing capability beside transaction signing.
- Test the new app and backend paths, including proof failures and absence of `/monitor` calls.

## Non-Goals

- No general wallet auth session, JWT, login, or account system.
- No Redis or new infrastructure.
- No on-chain receipt, attestation, proof, or claim-verification concepts.
- No domain-layer directional or execution-policy changes.
- No `@solana/web3.js` implementation logic.
- No dev bypass for unsigned `/monitor` enrollment.

## Decisions

- `/monitor` remains only as a tombstone: `410 Gone` with code `ENROLLMENT_UPGRADE_REQUIRED`.
- `/challenge` is idempotent while a challenge is active.
- A second `/challenge` call before expiry returns the same nonce, expiry, and message. It does not extend expiry.
- After expiry, `/challenge` replaces the row with a fresh nonce and fresh expiry.
- Signature encoding submitted by the app is base64.
- Wallet addresses remain base58 and are decoded with a strict local helper.
- Challenge expiry requires a new `/challenge` response and a new wallet signature.
- Raw signatures, raw nonces, and full verification messages must not be logged.

## Backend API

### `POST /wallets/:walletId/challenge`

Validates `walletId` as a Solana public key encoding. If malformed, returns:

```json
{ "code": "WALLET_MALFORMED" }
```

If no unexpired challenge exists, creates:

- `nonce`: 32 random bytes, hex encoded, 64 chars.
- `issued_at`: current clock timestamp.
- `expires_at`: current clock timestamp plus five minutes.

If an unexpired challenge already exists, returns it unchanged.

Response:

```json
{
  "walletId": "base58 wallet address",
  "nonce": "64-char hex nonce",
  "expiresAt": 1777750000000,
  "message": "CLMM wallet verification\n\nWallet: ...\nNonce: ...\nExpires: ..."
}
```

The `message` must be generated by `buildWalletVerificationMessage` on the backend. The client signs that exact string.

### `POST /wallets/:walletId/enroll`

Body:

```json
{
  "nonce": "64-char-hex-nonce",
  "message": "exact signed message",
  "signature": "base64 signature bytes"
}
```

Flow:

1. Validate `walletId`.
2. Validate body shape and nonce format.
3. Load the active challenge without consuming it.
4. Return `CHALLENGE_NOT_FOUND`, `CHALLENGE_EXPIRED`, or `CHALLENGE_MISMATCH` before signature verification when applicable.
5. Rebuild the expected message with `buildWalletVerificationMessage`.
6. Require the request `message` to match the expected message exactly.
7. Verify the Ed25519 signature with `verifyWalletSignature`.
8. After signature verification succeeds, atomically consume the challenge and enroll the wallet.

Invalid nonce, wrong message, invalid signature, and user-side signing failures must not consume the challenge. The challenge is consumed only after signature verification succeeds.

### `POST /wallets/:walletId/monitor`

Tombstone endpoint only:

- Always returns `410 Gone`.
- Body includes `{ "code": "ENROLLMENT_UPGRADE_REQUIRED" }`.
- Never calls `monitoredWalletRepo.enroll`.
- Has no dev bypass.

## Error Codes

New flow responses use stable structured codes:

| HTTP | Code |
| --- | --- |
| `400 Bad Request` | `WALLET_MALFORMED` |
| `400 Bad Request` | `CHALLENGE_NOT_FOUND` |
| `410 Gone` | `CHALLENGE_EXPIRED` |
| `409 Conflict` | `CHALLENGE_MISMATCH` for wrong nonce or wrong message |
| `401 Unauthorized` | `SIGNATURE_INVALID` |
| `410 Gone` | `ENROLLMENT_UPGRADE_REQUIRED` |

The app maps these to explicit enrollment outcome codes rather than generic connection failure.

## Storage

Add `wallet_challenges` in Postgres:

```sql
CREATE TABLE "wallet_challenges" (
  "wallet_id" text PRIMARY KEY,
  "nonce" text NOT NULL,
  "expires_at" bigint NOT NULL,
  "issued_at" bigint NOT NULL
);
```

Add `packages/adapters/src/outbound/storage/schema/wallet-challenges.ts` and export `walletChallenges` from `schema/index.ts`. Add the table to the Drizzle database schema registration.

The application port lives in `packages/application/src/ports/index.ts`:

```ts
export interface WalletChallengeRepository {
  issue(params: {
    walletId: WalletId;
    nonce: string;
    expiresAt: ClockTimestamp;
    issuedAt: ClockTimestamp;
    now: ClockTimestamp;
  }): Promise<{
    walletId: WalletId;
    nonce: string;
    expiresAt: ClockTimestamp;
    issuedAt: ClockTimestamp;
  }>;

  get(walletId: WalletId): Promise<{
    walletId: WalletId;
    nonce: string;
    expiresAt: ClockTimestamp;
    issuedAt: ClockTimestamp;
  } | null>;

  consumeAndEnrollIfMatches(params: {
    walletId: WalletId;
    nonce: string;
    now: ClockTimestamp;
    enrolledAt: ClockTimestamp;
  }): Promise<
    | { kind: 'consumed' }
    | { kind: 'not_found' }
    | { kind: 'expired' }
    | { kind: 'mismatch' }
  >;
}
```

`issue` atomically returns the existing unexpired challenge or stores and returns the supplied fresh challenge when no active row exists. It must not extend an active challenge expiry.

`consumeAndEnrollIfMatches` is the transactional final step. The Postgres adapter deletes the matching, unexpired challenge and upserts `monitored_wallets` in one database transaction. If no row is deleted, it returns a non-consumed state and does not enroll. This final state is still mapped to a structured response, because a concurrent request can consume or expire the challenge after the pre-verification `get`.

This avoids a two-commit sequence where a verified proof could consume a challenge and then fail before enrollment, or enroll without a successfully consumed challenge. Concurrent valid enroll attempts for the same challenge allow exactly one success.

The controller stays thin. If controller orchestration grows beyond simple request validation and response mapping, extract a `VerifyWalletEnrollment` use-case/coordinator. It must preserve repo boundaries: `WalletVerification.ts` remains in the HTTP adapter layer, and application code must not import WebCrypto or adapter helpers directly.

## Verification Helper

`packages/adapters/src/inbound/http/WalletVerification.ts` owns both helpers:

```ts
buildWalletVerificationMessage(params: {
  walletId: string;
  nonce: string;
  expiresAt: ClockTimestamp;
}): string

verifyWalletSignature(params: {
  walletId: string;
  message: string;
  signatureBase64: string;
}): Promise<boolean>
```

Message format:

```text
CLMM wallet verification

Wallet: {walletId}
Nonce: {nonce}
Expires: {isoTimestamp}
```

Verification rules:

- Decode wallet address with a strict base58 helper.
- Reject malformed wallet addresses and decoded public keys that are not 32 bytes.
- Decode signatures from base64.
- Reject malformed signatures and signatures that are not 64 bytes.
- Verify exact UTF-8 message bytes using WebCrypto Ed25519.
- Do not import `@solana/web3.js`.

## App Flow

Connection and enrollment are separate states:

```text
connect -> verify ownership -> enroll -> ready
```

The app must not navigate to the ready app state until verified enrollment succeeds.

Replace `enrollWalletForMonitoring` with typed API functions:

- `requestWalletChallenge(walletId)`
- `enrollWalletWithProof(walletId, proof)`

The app API client owns centralized structured error parsing so all enrollment failures produce typed outcome codes.

For each successful wallet connection path:

1. Request `/wallets/:walletId/challenge`.
2. Sign the returned exact `message`.
3. Verify the signing account still matches the target `walletId`.
4. Submit `{ nonce, message, signature }` to `/wallets/:walletId/enroll`.
5. Navigate only after enrollment returns success.

Browser and native wallet paths need explicit message-signing capability beside transaction signing:

- Browser: extend the ConnectorKit adapter wrapper with `signMessageBytes`.
- Native: add `signNativeMessage` using MWA `signMessages`.

Both signers must verify the signing account still matches the target wallet id. If message signing is unsupported, wallet id mismatches, the user rejects signing, or enrollment fails, the app returns an explicit enrollment outcome and never calls `/monitor`.

Challenge expiry is not recoverable by replaying the old proof. The user must receive a new challenge and sign the new message.

## Tests

Backend tests:

- Challenge issuance stores a 64-char nonce and five-minute expiry.
- Challenge issuance validates wallet format.
- Second `/challenge` before expiry returns the same nonce and expiry.
- Second `/challenge` before expiry does not extend expiry.
- `/challenge` after expiry replaces nonce and expiry.
- `/challenge` returns the exact backend-generated message.
- Missing challenge returns `CHALLENGE_NOT_FOUND`.
- Expired challenge returns `CHALLENGE_EXPIRED`.
- Wrong nonce returns `CHALLENGE_MISMATCH`.
- Malformed wallet returns `WALLET_MALFORMED`.
- Invalid signature returns `SIGNATURE_INVALID` and does not consume the challenge.
- Valid signature enrolls wallet and consumes the challenge.
- Replay of the same proof fails.
- `/monitor` returns `410 ENROLLMENT_UPGRADE_REQUIRED` and never enrolls.
- `WalletVerification` accepts a real Ed25519 test vector.
- `WalletVerification` rejects malformed wallet, malformed signature, wrong signature length, and message mismatch.
- Storage tests prove concurrent consume allows exactly one success.
- Storage tests prove consume plus enroll are transactionally coupled.

App tests:

- Enrollment calls `/challenge`, signs the returned message, then calls `/enroll`.
- Enrollment does not call `/monitor`.
- Failed enrollment does not navigate to the ready state.
- Unsupported message signing fails enrollment explicitly and does not call `/monitor`.
- Wallet mismatch fails enrollment explicitly and does not call `/monitor`.
- User rejection fails enrollment explicitly and does not call `/enroll` or `/monitor`.
- Challenge expiry maps to an explicit outcome and requires a new challenge/signature.
- Structured backend error codes are parsed through the centralized API client.

## Rollout Notes

Ship backend and app changes in the same release. Apply the database migration before enabling the new endpoints. Stale app clients that still call `/monitor` receive `410 ENROLLMENT_UPGRADE_REQUIRED` and cannot perform unsigned public enrollment.

Before implementing adapter code that touches Mobile Wallet Adapter, ConnectorKit, wallet standards, or WebCrypto Ed25519 behavior, check current official docs or Context7 per repo rules.
